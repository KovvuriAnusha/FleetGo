# Development setup

## Prerequisites

| Tool | Notes |
|------|-------|
| .NET SDK 10.0.100+ | `global.json` pins the 10.0.1xx band and rolls forward to your latest 10 SDK |
| .NET MAUI workloads | `dotnet workload install maui` (or `maui-android` / `maui-ios` individually) |
| JDK 17 | Required by the Android build |
| Android SDK | Ships with Visual Studio or Android Studio; API level 24+ |
| Xcode | macOS only, for iOS and Mac Catalyst |
| SQL Server (Phase 2+) | See "Database" below - LocalDB, Docker, or a full instance all work |

Check what is installed:

```bash
dotnet --info
dotnet workload list
```

## Everyday commands

```bash
# Backend + shared + tests (no MAUI workloads needed)
dotnet build tests/FleetGo.API.Tests
dotnet test --project tests/FleetGo.API.Tests
dotnet test --project tests/FleetGo.Mobile.Tests

# Run the API (Scalar UI opens at /scalar/v1)
dotnet run --project src/FleetGo.API

# Build every project, mobile heads included
dotnet build FleetGo.sln

# Run the app
dotnet build src/FleetGo.Mobile -t:Run -f net10.0-android
dotnet build src/FleetGo.Mobile -t:Run -f net10.0-ios
dotnet build src/FleetGo.Mobile -t:Run -f net10.0-maccatalyst
```

`dotnet build FleetGo.sln` requires the MAUI workloads, because the solution includes the mobile
project. Build the individual projects if you only want to work on the backend.

## Required local configuration (Phase 2+)

The API will not start without three things configured. All use `dotnet user-secrets`, so
none of them ever touches a file that gets committed:

```bash
cd src/FleetGo.API

# 1. A JWT signing key - at least 32 bytes (256 bits) once UTF-8 encoded. Generate one
#    rather than typing something memorable; this is what makes access tokens unforgeable.
dotnet user-secrets set "Jwt:SigningKey" "$(openssl rand -base64 48)"

# 2. A SQL Server connection string - see "Database" below for ways to get a SQL Server
#    instance to point this at.
dotnet user-secrets set "ConnectionStrings:FleetGoDatabase" "Server=localhost,1433;Database=FleetGo;User Id=sa;Password=<your-local-password>;TrustServerCertificate=True;"

# 3. (Phase 3+) An OTP hashing key - also at least 32 bytes once UTF-8 encoded. This is the
#    server-side pepper OtpService mixes into every one-time code before hashing it, which
#    is what keeps a 6-digit code from being brute-forceable offline straight from a leaked
#    OtpCodes table (see docs/architecture.md, "OTP hashing"). Use a different random value
#    than Jwt:SigningKey - they protect different things.
dotnet user-secrets set "Otp:HashingKey" "$(openssl rand -base64 48)"
```

Leaving any of these unset is a deliberate fail-fast: `Jwt:SigningKey` and `Otp:HashingKey`
are both checked at startup (`Program.cs` validates each via `ValidateOnStart()`) with an
error message pointing back here, and the database connection string is checked the first
time anything touches the database (a request, or `/health`) rather than silently falling
back to something insecure or wrong.

`Jwt:Issuer`, `Jwt:Audience`, `Jwt:AccessTokenLifetimeMinutes`, `RefreshToken:LifetimeDays`,
and the OTP tuning knobs (`Otp:CodeLength`, `Otp:ExpiryMinutes`, `Otp:MaxVerificationAttempts`,
`Otp:ResendCooldownSeconds`, `Otp:RequestRateLimit`, `Otp:VerifyRateLimit`) all have non-secret
defaults committed in `appsettings.json` - override them the same way
(`dotnet user-secrets set "Jwt:AccessTokenLifetimeMinutes" "5"`) only if you need to.

## Database

FleetGo uses EF Core with the SQL Server provider. Any of these gets you a local SQL Server:

- **Docker** (works on macOS/Linux/Windows):
  ```bash
  docker run -e "ACCEPT_EULA=Y" -e "MSSQL_SA_PASSWORD=<your-local-password>" \
    -p 1433:1433 --name fleetgo-sql -d mcr.microsoft.com/mssql/server:2022-latest
  ```
- **SQL Server LocalDB** (Windows only, ships with Visual Studio): connection string
  `Server=(localdb)\mssqllocaldb;Database=FleetGo;Trusted_Connection=True;TrustServerCertificate=True;`
- A full SQL Server instance you already have, local or remote.

Once `ConnectionStrings:FleetGoDatabase` is set (see above), create the schema:

```bash
cd src/FleetGo.API
dotnet tool install --global dotnet-ef   # once per machine
dotnet ef database update
```

### Adding a migration

```bash
cd src/FleetGo.API
dotnet ef migrations add <DescriptiveName>
```

This does not need a reachable SQL Server: `FleetGoDbContextFactory` (used only by the
`dotnet ef` tooling, never by the running app) reads your configured connection string if
one exists, or falls back to an inert placeholder purely so EF Core has something
syntactically valid to build the migration's SQL against.

> **Note on this repository's own migrations.** The initial `Users`/`Drivers`/`RefreshTokens`
> schema was written to run against a real `dotnet ef migrations add` locally, but could not
> be generated by an automated process in this environment (no .NET SDK / EF Core tooling
> available where this change was authored - see the Phase 2 implementation notes in the
> pull request). Run `dotnet ef migrations add InitialAuth` yourself the first time you pull
> this branch, after setting up the secrets above.
>
> The same is true of Phase 3's `OtpCodes` table: `OtpCode` and `OtpCodeConfiguration` are
> in place, but the migration itself could not be generated here either (same environment
> limitation). Run `dotnet ef migrations add AddOtp` yourself after pulling the
> `phase/3-otp-biometrics` branch and setting `Otp:HashingKey` above, then inspect the
> generated migration before applying it - in particular confirm the `OtpCodes` table has no
> plaintext code column (only `Salt`/`CodeHash` byte columns) and that its foreign key to
> `Users` cascades on delete, matching `OtpCodeConfiguration`.

## Running the tests

The test projects run on **Microsoft.Testing.Platform** (MTP): xUnit v3 hosts its own runner
inside the test executable, so there is no VSTest adapter and no `Microsoft.NET.Test.Sdk`.
`global.json` opts `dotnet test` into MTP mode:

```json
"test": {
  "runner": "Microsoft.Testing.Platform"
}
```

In MTP mode the project is passed as an option, not positionally:

```bash
dotnet test --project tests/FleetGo.API.Tests          # correct
dotnet test tests/FleetGo.API.Tests/FleetGo.API.Tests.csproj   # legacy VSTest syntax
```

Useful flags: `-c Release`, `--no-build`, `-f net10.0`, `--results-directory`,
`--show-test-results failed`.

`FleetGo.API.Tests` needs neither a JWT signing key nor a real SQL Server: `FleetGoApiFactory`
substitutes a fixed test-only signing key and an in-memory SQLite database (kept open for the
lifetime of each test class) for exactly this reason - see that file's comments for why SQLite
rather than the EF Core InMemory provider.

### "Testing with VSTest target is no longer supported by Microsoft.Testing.Platform"

This means `dotnet test` ran in VSTest mode against an MTP-based test project. The .NET 10
SDK dropped the VSTest bridge that used to make that work. Check that `global.json` contains
the `test.runner` setting above, that the test project sets
`<UseMicrosoftTestingPlatformRunner>true</UseMicrosoftTestingPlatformRunner>`, and that
neither `Microsoft.NET.Test.Sdk` nor `xunit.runner.visualstudio` is referenced.

## Ports and addresses

The API listens on `http://localhost:5266` (and `https://localhost:7266` under the `https` profile),
configured in `src/FleetGo.API/Properties/launchSettings.json`.

The mobile app resolves the API address per platform in `src/FleetGo.Mobile/Configuration/ApiSettings.cs`:

| Target | Address it uses | Why |
|--------|-----------------|-----|
| Android emulator | `http://10.0.2.2:5266` | The emulator is behind its own NAT; `10.0.2.2` is the host's loopback |
| iOS simulator | `http://localhost:5266` | Shares the host network stack |
| Mac Catalyst | `http://localhost:5266` | Runs on the host |
| Physical device | Your machine's LAN IP | Edit `ApiSettings`; device and machine must be on the same network |

## "The app says it cannot reach the API"

Work through these in order:

1. **Is the API running?** `curl http://localhost:5266/health` should return a JSON health report.
   As of Phase 2, a failing "database" entry in that report means the API is up but cannot
   reach SQL Server - check `ConnectionStrings:FleetGoDatabase` and that the server is running.
2. **Right address for the target?** See the table above. `localhost` inside an Android emulator
   means the emulator itself, not your Mac.
3. **Cleartext HTTP blocked?** Android permits it only for `10.0.2.2` and `localhost`, via
   `Platforms/Android/Resources/xml/network_security_config.xml`. A different host needs adding there
   (or, better, HTTPS).
4. **Using the HTTPS profile?** A simulator or emulator does not trust the ASP.NET Core development
   certificate by default. Prefer the `http` profile while developing, or run
   `dotnet dev-certs https --trust` and follow the platform-specific trust steps.
5. **Firewall** on the physical-device path - the Mac must accept inbound connections on 5266.

## Secrets

Never commit them. For local development:

```bash
cd src/FleetGo.API
dotnet user-secrets set "SomeSection:SomeKey" "value"
```

Secrets are stored outside the repository, keyed by the `UserSecretsId` in `FleetGo.API.csproj`.
Deployed environments supply the same keys as environment variables. As of Phase 2, this is how
`Jwt:SigningKey` and `ConnectionStrings:FleetGoDatabase` must be configured - see "Required local
configuration" above.
