# Roadmap

FleetGo is built in phases. Each phase is a vertical slice - backend, mobile and tests together -
so the app is runnable and demonstrable at the end of every one.

## Phase 1 — Foundation ✅

Solution, projects and references; shared contracts; OpenAPI and health checks; MAUI app with DI,
Shell and a landing page that verifies connectivity; integration and unit test projects; CI.

## Phase 2 — Identity and access 🔧 Implemented, pending build/test verification

- EF Core + SQL Server, `User` / `Driver` / `RefreshToken` entities and Fluent API configuration.
  The initial migration is written up but could not be generated by `dotnet ef migrations add` in
  the environment this phase was authored in (no .NET SDK available there) - see
  [docs/development-setup.md](development-setup.md#adding-a-migration) for the one-time command to
  run locally.
- Login endpoint issuing JWT access tokens and refresh tokens, with rotation and revocation
  (including reuse detection: presenting an already-revoked refresh token revokes the rest of that
  user's active sessions).
- Token storage on device using `SecureStorage` (Keychain / Android Keystore).
- `AuthenticationService` refreshes the access token proactively, shortly before it expires,
  rather than reactively on a 401. See "Deliberately not done yet" in
  [docs/architecture.md](architecture.md) for why the reactive refresh-and-retry handler from this
  line item was deferred, and what would need to change to add it.
- Login screen, session restore on launch, sign-out.

None of this has been compiled, run, or tested in the environment it was authored in - no .NET SDK
was reachable there. See the Phase 2 pull request notes for the exact verification steps a
developer needs to run locally before treating this phase as done.

## Phase 3 — OTP and biometrics 🔧 Implemented, pending build/test verification

- `OtpCode` entity and EF Core configuration (salted-HMAC hash only, never a plaintext code); the
  migration is written up but, like Phase 2's `InitialAuth`, could not be generated by
  `dotnet ef migrations add` in the environment this phase was authored in - see
  [docs/development-setup.md](development-setup.md#adding-a-migration) for the one-time
  `AddOtp` command to run locally.
- `POST /api/v1/auth/otp/request` and `/verify`, with expiry, single use, a per-user resend
  cooldown, and IP-partitioned ASP.NET Core rate limiting on both endpoints. Verification issues
  the same access/refresh token pair as password login - not a second authentication mechanism.
  `IOtpSender` keeps the API decoupled from any specific SMS provider (no Twilio or other paid
  dependency was added); the development sender it ships with is structurally prevented from
  registering outside Development/Testing.
- Android SMS Retriever autofill (no `READ_SMS`/`RECEIVE_SMS` permission); iOS/Mac Catalyst
  one-time-code keyboard support. Manual code entry always works on every platform.
- Biometric unlock for an existing, already-authenticated session via `IBiometricAuthenticator`
  (AndroidX Biometric / `LocalAuthentication`) behind a platform-agnostic
  `IBiometricUnlockCoordinator`. Biometrics never create an account, never replace server
  authentication, and never mint a token on their own - see "Phase 3: OTP and biometric unlock" in
  [docs/architecture.md](architecture.md) for the full reasoning.
- API and Mobile.Core test coverage for all of the above, using test doubles for the OTP sender,
  the biometric authenticator and the preference store - no real SMS delivery, biometric hardware,
  or third-party service is required to run the tests.

None of this has been compiled, run, or tested in the environment it was authored in - no .NET SDK
was reachable there. See the Phase 3 pull request notes for the exact verification steps (restore,
build, `dotnet ef migrations add AddOtp`, API tests, Mobile tests) a developer needs to run locally
before treating this phase as done, and for the specific areas flagged there as unverified (exact
AndroidX Biometric/Play Services API shapes and the two new Android NuGet package versions).

## Phase 4 — The working day

- Vehicle, customer, route, stop and package APIs
- Pagination, filtering and sorting on list endpoints
- Driver dashboard, route list, stop detail
- Search and filter on device

## Phase 5 — Offline first

- SQLite local store and a local-first read path
- Outbox for mutations made offline, with conflict handling
- Background synchronisation and retry with exponential backoff
- Connectivity detection and honest UI state

## Phase 6 — Proof of delivery

- Camera capture, digital signature, document upload/download
- Barcode and QR scanning for packages
- POD submission endpoint with attachments

## Phase 7 — Location

- Foreground and background location tracking, with the platform permission flows
- Batched location upload endpoint
- Map and route visualisation

## Phase 8 — Notifications and deep links

- Device registration endpoint and push delivery
- Deep links from a notification into the right stop

## Phase 9 — Payments

- Sandbox payment gateway integration for cash-on-delivery and card capture
- Payment records and reconciliation endpoints

## Phase 10 — Production readiness

- Structured logging and diagnostics, correlation IDs
- Resilience policies, timeouts and circuit breakers
- App version and forced-update handling
- Release pipelines for the mobile heads

*Phases after 2 may be reordered as the app takes shape.*
